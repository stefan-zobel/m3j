Modula-3 on the JVM

Value records, VAR parameters, nested procedures, structural types and unsigned words, compiled for a virtual machine that was built for Java.

Modula-3 in one paragraph

Modula-3 was designed in the late 1980s at Digital Equipment Corporation's Systems Research Center and Olivetti Research as a successor to Modula-2. It put things together in a small language that were rarely found together at the time: garbage collection, threads and exceptions as part of the language, objects with single inheritance, generic modules, and interfaces compiled separately from their implementations. Operations that can break memory safety are allowed only in modules marked UNSAFE; everything else is safe by construction. Java programmers will recognize much of it, and Python's class mechanism is, in the words of its own tutorial, a mixture of those of C++ and Modula-3. Today the language lives on in a single maintained implementation, Critical Mass Modula-3 (CM3), a descendant of DEC's original compiler.

An interface and its implementation look like this:

INTERFACE Stack;

TYPE T <: ROOT;            (* opaque: clients see no fields *)

EXCEPTION Empty;

PROCEDURE New (): T;
PROCEDURE Push (s: T; x: INTEGER);
PROCEDURE Pop (s: T): INTEGER RAISES {Empty};

END Stack.
MODULE Stack;

REVEAL T = BRANDED OBJECT
    items: REF ARRAY OF INTEGER;
    n := 0;
  END;

PROCEDURE New (): T =
  BEGIN
    RETURN NEW (T, items := NEW (REF ARRAY OF INTEGER, 8));
  END New;

PROCEDURE Push (s: T; x: INTEGER) =
  BEGIN
    IF s.n = NUMBER (s.items^) THEN
      WITH bigger = NEW (REF ARRAY OF INTEGER, 2 * s.n) DO
        SUBARRAY (bigger^, 0, s.n) := s.items^;
        s.items := bigger;
      END;
    END;
    s.items[s.n] := x;
    INC (s.n);
  END Push;

PROCEDURE Pop (s: T): INTEGER RAISES {Empty} =
  BEGIN
    IF s.n = 0 THEN RAISE Empty END;
    DEC (s.n);
    RETURN s.items[s.n];
  END Pop;

BEGIN
END Stack.

m3j

m3j compiles Modula-3 to Java class files. A compiled program needs a JDK 25 and nothing else: no C compiler, no native runtime. The front end is a port of CM3's, so programs get the same diagnostics; the back end is new and writes bytecode with the JDK's Class-File API (java.lang.classfile). Where the language definition leaves a choice to the implementation, such as evaluation order, the results at the edges of the number ranges or the text of runtime errors, m3j does what a program compiled natively by CM3 for 64-bit Windows does, so CM3's test suite can serve as the oracle.

A good part of m3j is written in Modula-3 and compiled by m3j itself: not counting tests, about 58 percent of the source lines of the toolchain are Modula-3 (the library, the build system, the language server, the stub generator for network objects and the Modula-3 toolkit both of these run on); the compiler and the core of the runtime are Java.

The JVM brings much of what Modula-3 needs: garbage collection, threads, exceptions, a bytecode verifier and a very good JIT compiler. What it does not bring is just as clear. Its type system is Java's: classes are identified by name, every object lives on the heap behind a reference, there are no pointers to local variables, fields or array elements, no unsigned integers, and no nested functions that can reach the local variables of the function around them. Modula-3 has all of these. The rest of this article is about how m3j bridges each gap, under two constraints: the results must be those of the native compiler, edge cases included, and the bytecode must be the kind the JIT compiles well, with unboxed values, static calls, small methods and checks that are plain compares.

1. Integers that behave like a 64-bit machine

INTEGER has 64 bits on the reference platform, so it is a JVM long. Smaller types are stored compactly: a subrange such as [0..255] is held in the smallest JVM type that fits, CHAR in a byte (read back with & 0xFF), an enumeration of up to 256 values as its ordinal in a byte, and a set of up to 64 elements as a long bit mask. Arithmetic is done in int only where an analysis of the bounds of the operands proves that the long result would be the same.

Overflow is where the two languages agree for free: CM3 does not check it and wraps around, and so does the JVM. Elsewhere, straightforward Java gives the wrong answer:

Modula-3ResultNaive JavaResult
-7 DIV 2-4-7 / 2-3
-7 MOD 21-7 % 2-1
Word.Shift (1, 64)01L << 641
Word.LT (1, -1)TRUE1L < -1Lfalse
ROUND (-2.5D0)-3Math.round(-2.5)-2
TRUNC (1.0D30)FIRST (INTEGER)(long) 1e30Long.MAX_VALUE

DIV and MOD round toward minus infinity, so they become Math.floorDiv and Math.floorMod, which the JIT turns into multiplications when the divisor is a constant. The interface Word treats an INTEGER as an unsigned 64-bit word; its comparisons and divisions are Long.compareUnsigned, Long.divideUnsigned and Long.remainderUnsigned, which are JIT intrinsics. Java masks a shift count to its low six bits, while Word.Shift by 64 or more gives 0, so a shift by a count that is not a constant gets a guard. ROUND rounds halves away from zero, unlike Math.round. And a conversion of a value that does not fit gives FIRST (INTEGER) natively, because that is what the x86-64 conversion instruction returns for anything out of range, while the JVM saturates and maps NaN to 0; a small runtime helper corrects the result.

Range checks, for example when a value is assigned to a subrange variable or used as an array index, are inline compares, and they are left out wherever the bounds analysis shows that they cannot fail.

2. Records are values, arrays are flat

A Modula-3 record is a value, like a C struct: assignment copies it.

TYPE Point = RECORD x, y: INTEGER END;
VAR p, q: Point;

p.x := 3;
q := p;          (* a copy *)
q.x := 7;        (* p.x is still 3 *)

The JVM has no value types yet, so each record type becomes a class with typed fields, and a record variable holds its own object for its whole life. Assignment never replaces that object; it copies into it, through a method generated for the type. A field that is itself a record or a fixed array holds an object that is created with the outer record and never replaced either, so a nested record costs one allocation when its container is created and none afterwards. In Java terms, the code above becomes:

public class Td1599f69 implements Rec {      // RECORD x, y: INTEGER END
    public long x, y;
    public void copyFrom(Td1599f69 other) { ... }
    public boolean eq(Td1599f69 other) { ... }
}

Main.p.x = 3;
Main.q.copyFrom(Main.p);
Main.q.x = 7;

The class is named after the type's fingerprint, for reasons that section 6 explains. Records passed by value are copied by the caller, except when the argument is a fresh value, such as the result of a call or a constructor, which nobody else can see.

Fixed arrays are flat and row-major in an array of the element's storage type: ARRAY [0..9] OF ARRAY [0..9] OF INTEGER is one long[100], not an array of arrays, and an array of CHAR is a byte[]. A row such as a[i] is not an object but a pair of the storage and an offset, with a shape known at compile time. Array assignment is System.arraycopy, and = uses Arrays.equals and Arrays.mismatch on ranges; both are intrinsics. CM3 compares such arrays as their bits, so 0.0 and -0.0 differ and a NaN equals itself, which happens to be exactly what Arrays.equals does for double[].

3. Open arrays and SUBARRAY without copies

A procedure can take an array of any length, and SUBARRAY passes a slice of another array without copying it:

PROCEDURE Sum (READONLY v: ARRAY OF INTEGER): INTEGER;

Sum (SUBARRAY (a, 1, 3))     (* a[1], a[2], a[3] *)

Since a fixed array is already storage plus offset, an open array parameter is passed as three JVM values: the storage, the offset and the length, with one more int for each further open dimension. The signature in the class file is

public static long Sum(long[] v, int offset, int length)

and SUBARRAY (a, 1, 3) is just the arguments a, 1, 3, after a check that the slice lies inside a. The rows of a multi-dimensional array are passed the same way. A heap-allocated REF ARRAY OF T is a small object that holds the storage and the dimensions; inside a loop its storage, offset and length are copied into locals, so that the JIT can hoist the bounds checks out of the loop.

4. VAR parameters: references to anything

A VAR parameter is passed by reference, and the actual argument can be any variable: a local, a global, a field, an array element.

PROCEDURE Swap (VAR a, b: INTEGER) =
  VAR t := a;
  BEGIN
    a := b; b := t;
  END Swap;

Swap (i, j);
Swap (arr[k], point.x);

The JVM cannot point at a local variable, a field or an array element. For records, fixed arrays and large sets the problem does not arise: the callee gets the object, or the storage and offset, and writes into it. For scalars m3j uses typed reference objects: one abstract class per JVM type (LongRef, IntRef, DoubleRef, FloatRef, ObjRef) with small final subclasses for the kinds of places:

  • a cell for a local variable that is passed VAR somewhere; the variable lives in its cell for its whole life, so a call allocates nothing;
  • an element reference per storage kind, holding an array and an index;
  • a class generated per field of a record or object, per frame field and per global variable.

Swap itself is then ordinary code against the abstract class. From the class file:

public static void Swap(LongRef a, LongRef b) {
    long t = a.get();
    a.set(b.get());
    b.set(t);
}

// Swap (i, j) for the module variables i and j:
Swap(new m3_m_Main$$i(), new m3_m_Main$$j());

Each call site sees only a few concrete classes, so the calls of get and set inline, and once Swap is inlined into its caller, escape analysis removes the allocation of the reference objects as well. INC, DEC and assignment never create references.

A READONLY parameter is a subtle case: the language requires that the callee see a change made to the actual variable through an alias during the call, so it is passed by reference when the argument is a variable of the same type, and as a copy otherwise.

5. Nested procedures and their frames

Procedures can be declared inside procedures and use their variables:

PROCEDURE Sum (READONLY v: ARRAY OF INTEGER): INTEGER =
  VAR total := 0;
  PROCEDURE Add (x: INTEGER) =
    BEGIN INC (total, x) END Add;
  BEGIN
    FOR i := FIRST (v) TO LAST (v) DO Add (v[i]) END;
    RETURN total;
  END Sum;

Java has nothing comparable: a lambda can only capture effectively final values. m3j finds the variables that nested procedures use and moves just those into a frame object generated for the procedure; all others stay JVM locals. A nested procedure is a static method that takes the frame as its first parameter, the static link of classic compilers:

final class Main$F$Sum { long total; }

static long Sum(long[] v, int offset, int length) {
    var f = new Main$F$Sum();
    f.total = 0;
    for (long i = 0; i <= length - 1; i++)
        Sum$Add(f, v[offset + Rt.index(i, length)]);   // with the subscript check
    return f.total;
}

static void Sum$Add(Main$F$Sum f, long x) { f.total += x; }

A nested procedure receives a frame only if it, or a procedure it calls, needs a variable of an enclosing procedure; otherwise it is an ordinary static method. Frames of deeper nesting levels are chained through a field.

Procedures are also values. For each JVM signature m3j generates one functional interface. A top-level procedure used as a value is created with LambdaMetafactory in an accessor method of its module, so the same procedure is always the same object; that matters, because Modula-3 compares procedure values with =. A nested procedure used as a value is a closure object that holds the procedure and its frame. Modula-3 allows passing such a value as an argument but not storing it in a variable; m3j enforces this at compile time where it can and at run time otherwise.

6. Structural types in a nominal VM

In Java, two classes with the same fields are different types. In Modula-3, type identity is structural: two declarations of REF RECORD head: INTEGER; tail: List END in different modules denote the same type, and only the keyword BRANDED makes a type unique. The JVM, however, identifies a class by its name.

m3j names the class of a record, reference or object type after a fingerprint of its structure, the same in every compilation unit. Every unit that needs the type generates the class; the copies are identical, and the linker keeps one. As a result, TYPECASE, NARROW and ISTYPE are plain instanceof and checkcast instructions, with no registry of types at run time:

// List = REF RECORD head: INTEGER; tail: List END
public class T51c44b24 implements Rec {            // the record
    public long head;
    public T51c44b27 tail;
}
public final class T51c44b27 extends T51c44b24 { } // REF of it: List

The class of REF R is a subclass of the class of R, so l.head through a reference is a single getfield instead of two. The default values of record fields are not part of the class: types that differ only in their defaults are the same type, so defaults are set where a variable is created, from its declared type.

NIL belongs to every reference type, while instanceof is false for null; so a TYPECASE tests for NIL before anything else. One with many arms uses SwitchBootstraps.typeSwitch, the bootstrap behind Java's pattern-matching switch.

7. Methods that must not override

A subtype in Modula-3 can declare a new method with the same name as a method of its supertype. That method hides the old one; it does not override it:

TYPE
  A = OBJECT METHODS m (): TEXT := MA END;
  B = A OBJECT METHODS m (): TEXT := MB END;  (* a second method m *)

VAR b := NEW (B);  a: A := b;

a.m ()     (* "A.m": the method of A, although a is a B *)
b.m ()     (* "B.m" *)

On the JVM, a method with the same name and descriptor in a subclass always overrides. So the JVM name of a method carries the fingerprint of the type that declares it:

public class m3.t.T0d8bc911 extends m3j.rt.M3Object {      // A
  public java.lang.String m_0d8bc911();
}
public class m3.t.Tef9bf88f extends m3.t.T0d8bc911 {       // B
  public java.lang.String m_ef9bf88f();
}

An OVERRIDES clause overrides the JVM method of the declaring type, so dispatch is an ordinary invokevirtual. The body of a JVM method calls the procedure bound to the method statically, and a method left NIL raises the runtime error of the reference. NEW (T, m := P), which binds a method for one object, creates an instance of a subclass generated for that expression.

Opaque types, like Stack.T above, show where the JVM is actually easier than native code. A client of Stack knows nothing about the fields of T; a native compiler must therefore compute their offsets when the program is linked or started. In a class file, fields and methods are referenced by name and resolved lazily at first use, so no offsets are needed at all. Only the module that holds the full revelation generates the class, named after the opaque type.

8. Exceptions, RAISES and FINALLY

Each EXCEPTION declaration becomes a class that carries its argument and the source position of the RAISE, created without a Java stack trace, so raising costs little more than an allocation. TRY EXCEPT becomes entries of the exception table, and TRY FINALLY is generated the way javac does it, with the FINALLY part on every exit, including RETURN and EXIT. A jump out of several nested TRY statements runs their FINALLY parts from the inside out. The language defines EXIT and RETURN in terms of exceptions, so the ELSE arm of a TRY EXCEPT sees them, as with the native compiler.

A RAISES clause is the opposite of a Java throws clause: it is checked at run time, not at compile time. A procedure without one may raise nothing, and an exception that escapes and is not listed becomes a checked runtime error at the place of the RAISE. m3j wraps the body of a procedure in a handler for that, but leaves it out when every RAISE and every call in the body can only raise listed exceptions (a procedure that is called checks its own clause). Pop above, whose only RAISE is Empty, gets no handler.

Checked runtime errors, such as a subscript out of range or a dereference of NIL, end the program with the message of the native compiler, with the line taken from the class file's line number table:

***
*** runtime error:
***    An array subscript was out of range.
***    file "Main.m3", line 19
***

Where the JVM detects such an error itself (ArithmeticException, IndexOutOfBoundsException, NullPointerException, ClassCastException, StackOverflowError), it is translated into Modula-3's runtime error wherever Modula-3 code can observe it: in an EXCEPT ELSE, a FINALLY, a LOCK and at the top of the program.

9. Modules: initialization order and late binding

A module becomes a class with static fields for its variables and static methods for its procedures. Its body, however, is an explicit initialization method and not the class initializer <clinit>. Modula-3 defines the order in which module bodies run from the import graph, cycles included, whereas the JVM initializes a class whenever it is first touched. The linker of m3j computes the order as CM3's runtime does and writes a main class that calls the initialization methods in that order, then runs the program in a thread with a large stack.

An interface in Modula-3 does not say which module implements it. Any module can export it, and several modules can each implement part of it. That is known only when the program is linked, after the clients were compiled. Calls into an interface therefore use invokedynamic: on the first call the bootstrap method looks the procedure up in the link table and returns a ConstantCallSite for the static method of the exporting module, which the JIT then treats like a direct invokestatic. This is IO.Put (text), whose second parameter, a writer, has the default NIL:

170: aconst_null
171: checkcast     #99      // class m3/t/T62761487
174: invokedynamic #112, 0  // InvokeDynamic #1:Put:(Ljava/lang/String;Lm3/t/T62761487;)V

Calls within a unit, and calls from the exporting module itself, are plain invokestatic.

10. Code the JIT compiles well

  • Method size. HotSpot does not compile methods larger than 8000 bytes of bytecode at all; they run in the interpreter forever. Generated code, such as a CASE with hundreds of arms, can easily exceed that. m3j measures instead of estimating: it generates a procedure, parses the result back with the Class-File API, and if a method is too large, it moves runs of statements into separate chunk methods that share the procedure's frame. A chunk returns a code that tells its caller whether its statements completed, executed a RETURN or left a loop with EXIT. This is tested by lowering the limit to a few hundred bytes and compiling large real programs, which then consist of thousands of chunks and must give the same results.
  • Module bodies. A module body runs once, so the JIT could compile a loop in it only by on-stack replacement and without a profile for the code that follows. Each loop in an initialization method therefore becomes a method of its own.
  • Loops and switches. A FOR loop gets an int counter when the counter, the limit and the step fit in int and the last increment cannot overflow, which makes it a counted loop for C2. A CASE with dense labels becomes a tableswitch or lookupswitch.
  • Constant tables. An array constant of numbers, characters or small sets is a dynamic constant (ldc of a CONSTANT_Dynamic), built once from a string that holds its elements. Large tables need no code, unlike in javac's output, where an array initializer is one store per element in the class initializer.
  • Exact types. Every parameter has its precise JVM type in the descriptor, never Object plus a cast.

11. Threads and locks

A Modula-3 MUTEX is not re-entrant: locking a mutex that the thread already holds is an error, not a second hold count, so a Java monitor will not do. m3j's mutex knows its holder. Readers and writers lock their mutex for every character, so the lock has to be cheap: as long as a program has not forked a thread or handed a procedure to Java, which might call it from any thread, the holder is set and cleared with plain writes; after that, with a compare-and-set. Thread.Alert, Modula-3's cooperative cancellation, is a per-thread flag combined with Thread.interrupt, so that blocked waits wake up.

12. Calling Java

An interface can stand for a Java class. The compiler checks the declarations against the class when the interface is compiled, and a call is the JVM instruction itself, not reflection:

<*EXTERNAL "java.util.ArrayList":JAVA*> INTERFACE ArrayList;

IMPORT Java, JavaObject;

TYPE T <: JavaObject.T;                      (* the class java.util.ArrayList *)

PROCEDURE New (): T;                         (* the constructor *)
PROCEDURE add (self: T; e: REFANY): BOOLEAN;
PROCEDURE size (self: T): Java.Int;

END ArrayList.

Modula-3 object types can extend Java classes or implement Java interfaces, and Modula-3 procedures can be passed where Java expects a functional interface. A Java exception that reaches Modula-3 code becomes the Modula-3 exception Java.Exception, which carries the throwable.

How it is checked

  • The test programs of CM3's own suite are compiled and run, and their output is compared with the expected output of the suite. Every generated class must pass the verifier of the Class-File API.
  • Further programs are compared with their output when built natively by CM3, among them edge cases of number formatting, floating point, pickles and pathnames, and threads under load.
  • Two random program generators compare m3j with CM3. The first produces expressions and computes every expected value itself, so it can tell which compiler is wrong. The second produces statements, procedures and data: nested procedures that use their parents' variables, VAR parameters bound to overlapping places, objects, exceptions, several modules with cycles of imports. Each of its programs is compiled twice, once normally and once with a tiny method size limit, so that split methods are compared too, and a failing program is reduced automatically.
  • Large programs: CM3's own front end, about 600 units, compiled by m3j and run on the JVM, must produce the same intermediate code, byte for byte, and the same diagnostics as the front end of m3j; CM3's stub generator for network objects, compiled by m3j, must write the same stubs as the native one; and network object programs built by m3j and by CM3 must talk to each other and send the same bytes.

The rest of the toolchain

  • m3build, CM3's build system with its interpreter for the m3makefile language, compiled by m3j: packages are built from the same m3makefiles as with CM3.
  • Network objects, Modula-3's distributed objects with distributed garbage collection, with CM3's runtime and stub generator; programs built by m3j interoperate with programs built natively.
  • A language server, CM3's, on the Modula-3 toolkit m3tk, also compiled by m3j: errors while typing, hover, go to definition, the outline of a file and completion, with an extension for Visual Studio Code and settings for Neovim, Emacs, Helix and Kate.
  • Libraries for current needs, mostly thin layers over the JDK: an HTTP server and client, TLS, JSON, XML, SQL through JDBC, SSH and SFTP, regular expressions, compression and cryptography.

What is not supported: UNSAFE modules, since a safe language on a safe VM leaves no room for them, and CM3's GUI libraries.

Trying it

m3j needs a JDK 25 or later. The release, one archive for Windows, Linux and macOS, holds the jars, the libraries and the start scripts. Once its directory bin is on the PATH, a program is compiled in memory and run at once:

MODULE Main;

IMPORT IO;

BEGIN
  IO.Put ("Hello, world\n");
END Main.
m3j Main.m3 -run

The sources, the documentation and the design notes of the back end, which explain every decision in this article in more detail, are at github.com/stefan-zobel/m3j.
