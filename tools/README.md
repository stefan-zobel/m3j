# Tools

The tests `run_jvm.py`, `diff_test.py` (without `--record`), `split_test.py`,
`cli_test.py`, `m3front_test.py`, `stubgen_test.py`, `build_test.py` (its parts `quake` and `cases`), `bind_test.py` and `bundle_test.py` (without `--record`), `net_test.py` (without `--cm3` and `--record`), `lsp_test.py`, `perf.py` (without `--native`) and `dump_test.py` (without `--record`) need
only the tree: their inputs and the recorded results of cm3 are in `tests`
(`tests/m3tests` has the tests of cm3's m3tests that m3j runs, `tests/diff/src` of the test
programs and examples, `tests/pkg` of the packages they use, `tests/m3front` of CM3's front end, `tests/stubgen` of CM3's stub generator, `tests/bundle` of m3bundle, `tests/bind` of m3jbind, `tests/net` of programs that talk over TCP, `tests/quake` and `tests/build` of m3build, `tests/lsp` of the language server). The other
tools compare with a cm3 installation or cm3 sources outside the tree,
given as arguments.
`coverage.py` needs JaCoCo (0.8.14 or later), unpacked below `download` or
given with `--jacoco`. The tests that start JVMs (`run_jvm.py`,
`diff_test.py`, `split_test.py`, `cli_test.py`, `m3front_test.py`, `dump_test.py`,
`pkg_gate.py`, `front_test.py`) pass each `--jvm-arg=ARG` to every JVM
they start (`stubgen_test.py` to the JVM that compiles stubgen); `coverage.py` uses this for its agent. With
`--jvm-arg=-Dm3j.maxMethod=200`, m3j splits methods over 200 bytes instead
of 8000 (see `docs/BACKEND.md`), so that `diff_test.py` and `run_jvm.py`
test the chunks of split procedures on every program.

| Tool | Purpose |
|---|---|
| `cm3-keep-side-ir.patch` | Fix for the builder of the reference cm3, so that `cm3 -keep` writes the M3CG side file (`.mc`, `.ic`) in the C back-end mode. |
| `cm3-tee.patch` | Fix for `M3CG_Tee` in `m3middle` of the reference cm3 (four bugs that `cm3 -keep` exposes in the C back-end mode: nested procedures, `case_jump` labels, `declare_object`, the first label). |
| `cm3-external.cfg` | Configuration for the reference cm3 that selects the external back-end mode, in which the front end writes the binary M3CG file directly (point `M3CONFIG` at it, and it finds the installation in `cm3` in the root of m3j; copied as `cm3.cfg` into a package directory, it needs `CM3_INSTALL`, the directory of the installed cm3; `cm3 -keep` then leaves the `.mc` and `.ic` files, although the missing `cm3cg` makes the build fail). |
| `gen_polybasis.py` | Generates `src/main/java/m3j/fingerprint/PolyBasis.java` from CM3's `PolyBasis.i3`: `python3 tools/gen_polybasis.py cm3-src`. |
| `gen_fp_cases.py` | Generates the input of the fingerprint test, `tests/fingerprint/cases.txt` and `faults.txt`. |
| `fpdump/` | Modula-3 program (build with `cm3` in `tools/fpdump`) that runs CM3's `Fingerprint`, `M3FP` and `Poly` on the test cases. |
| `gen_mid_cases.py` | Generates the input of the m3middle test, `tests/middle/cases.txt` and `faults.txt`. |
| `middump/` | Modula-3 program (build with `cm3` in `tools/middump`) that runs CM3's `TInt`, `TWord`, `TFloat`, `Convert`, `M3Buf`, `M3ID` and `Target` on the test cases. |
| `dump_test.py` | Differential tests on recorded results: `python3 tools/dump_test.py fingerprint` (or `middle`) compares `m3j.tools.FpDump` (`MidDump`) with `tests/SUITE/expected.txt` and checks the fault cases; `--record EXE` records the expected results with the Modula-3 program. |
| `cg_test.py` | M3CG test: converts the binary intermediate code files below the given directories to text with cm3's `m3cgcat` and with `m3j.tools.CgCat`, and compares the results. |
| `front_test.py` | Front-end test: for packages built by cm3 with `cm3 -keep -commands > build.log 2>&1`, runs `m3j.tools.FrontDump` (the front-end runs of the log, with the same options) and compares the M3CG text of every unit and the diagnostics with cm3's; `--jvm-arg=ARG` passes options such as a coverage agent to the JVM. |
| `run_jvm.py` | Back-end test: compiles the programs of m3tests (`p0`–`p2`, `r0`, by test or group) with m3j, runs them and compares stdout and stderr with the expected files of m3tests (`tests/m3tests`); `--compile c0 c1` only compiles the compile tests and checks that every class verifies. The tree has only the tests that m3j runs (not those that need UNSAFE code or C sources, the tests of the build system and the group `x0`, whose programs a person checks); such a test given by its directory is skipped. |
| `m3front_test.py` | Test of the back end on a large program: compiles CM3's front end (`tests/m3front`: m3front, m3middle and a driver) with m3j, then compiles test cases (programs of m3tests by test or group, `lib`, the library of m3j, and `self`, the front end itself) with m3j's driver (`-mc`, which writes the binary M3CG of every unit and the list of the units compiled) and with the compiled front end on the same list, and compares the M3CG bytes of every unit, the diagnostics and the exit code; for a difference in the code it shows the first differing line as text. |
| `stubgen_test.py` | Test of the back end on a second large program: compiles CM3's stub generator for network objects (`tests/stubgen`: stubgen and the toolkit m3tk it is built on) with m3j, runs it on the JVM for the network object types of CM3's packages (`tests/stubgen/cases.list`, each with `-v1` and `-v2`) and compares the stubs it writes, byte for byte, its output and its exit code with those of stubgen built by cm3, recorded in `tests/stubgen/expected` (`--record` builds stubgen with cm3, from `--stubgen DIR`, by default `cm3-src/m3-comm/stubgen`, and records them). |
| `bundle_test.py` | Test of m3bundle of cm3 (`tools/m3bundle`, which `build.sh` compiles with m3j into `m3bundle.jar`): runs it on the JVM for the cases of `tests/bundle/cases.list` (texts with the characters that it escapes, every byte value, files of several blocks, names with quotes, an option file, errors of its parameters and of a missing file), each in a directory with a copy of `tests/bundle/data`, and compares the interface and module that it writes, byte for byte, its output and its exit code with those of m3bundle of cm3, recorded in `tests/bundle/expected` (`--record --m3bundle EXE` records them). |
| `m3build/` | m3build, the build system of m3j (`build.sh` compiles it with m3j into `m3build.jar`): in `src/m3quake` the quake interpreter of CM3 5.12.0 (`m3-sys/m3quake`), in `src/cm3` the parts of the driver of cm3 that read m3makefiles (`m3-sys/cm3`: `Main`, `Makefile`, `M3Build`, `M3Unit`, `M3Loc`, `Arg`, `Msg`, `Utils`, `Dirs`, `M3Options`, `M3Timers`), in `src/m3middle` and `src/etimer` the units of m3middle and libm3 that they use, in `src/derived` their generic instances, with their copyrights; the UNSAFE modules made safe and the other changes for m3j are noted in the head of each file. In place of cm3's builder, which compiles units and links objects, `src/cm3/Builder.m3` gives the units of a package to the compiler of m3j (the interface `src/m3j/M3jCompile.i3`, which the runtime implements with `m3j.jvm.Compile`); `m3j.cfg` is the configuration that m3build reads in place of `cm3.cfg` (`build.sh` copies it next to the jars). |
| `build_test.py` | Tests of m3build: `python3 tools/build_test.py [quake] [exports [PKG...]] [cases [CASE...]] [packages [PKG...]]`. `quake` runs the tests of cm3's quake interpreter (`tests/quake`) as an m3makefile, against the output of `cm3 -build` recorded on AMD64_NT. `exports` runs `m3build -exports` on a copy of the sources (`--src`, by default `cm3-src`) of each package of a cm3 installation (`--cm3`, by default `cm3`) and compares the units, templates and imports of its `.M3EXPORTS` with cm3's (`tests/build/exports.list` names the packages that differ for a reason: KNOWN). `cases` builds the packages of `tests/build` with the commands of `tests/build/cases.list` (programs, generics, libraries installed and imported, overrides, bundles, network objects with a server and a client, Java classes of a jar and a directory, a jar passed on by a library, errors) against output written by hand (`tests/build/expected`). `packages` builds packages of cm3 from a copy of their sources with their own m3makefiles: libraries that it installs, and programs that use them, whose output must be that of `diff_test.py` (APPROX within its tolerance). |
| `gen_lib_exports.py` | Writes the `.M3EXPORTS` of the packages that m3j brings (`lib/PKG/JVM`), through which m3build imports them, from those that a cm3 installation has for them (only the units that `lib` has, m3j's own added; a package that `lib` does not have is not imported), and copies the quake templates that they export from the cm3 sources into `lib`; the same for the source packages m3tk and m3tk-misc of `tests/stubgen`, which the language server imports through its `m3overrides`. Run after a change of the units of `lib`. |
| `langserver/` | CM3's language server (`m3-tools/langserver` of CM3 5.12.0, MIT license), which `build.sh` builds with m3build from its `m3makefile` into `m3_lang_server.jar`: the Language Server Protocol over the standard input and output, with the errors, hovers and declarations of m3tk; the changes for m3j and for Windows are noted in the head of each unit. `langserver/vscode` is an extension for Visual Studio Code (the language, its grammar and a client of the server, without other packages). See `langserver/README.md`, also for other editors. |
| `lsp_test.py` | Tests of the language server: in a copy of the packages of `tests/lsp/pkgs` (in a directory whose name has a space), each session of `tests/lsp/sessions` sends its messages to `m3_lang_server.jar` (`initialize`, the opening and changing of files, hovers, declarations, definitions and type definitions in the same file, in an interface of the package, in `lib` and in a library of `m3overrides`, from files of `lib` itself, wide literals, forms of the language that m3tk has to accept or to survive, the values of calls of `Long` and `Word`, names used only in an `ASSERT`, `DEBUG` or `FATAL` pragma, errors and warnings after incremental changes, messages that are wrong, the end of the input, `shutdown` and `exit`), and what it sends back, with the work directory as `<work>`, must be `tests/lsp/expected/SESSION.json`, checked by hand (`--record` writes it). With node (`--node`, or on the PATH; else SKIP) it also runs `langserver/vscode/test/smoke.js`: the client of the extension, and the extension with the API of Visual Studio Code replaced by a mock, against the server. |
| `bind_test.py` | Tests of m3jbind (`m3j.jvm.Bind`, which writes the interfaces that bind Java classes; see "Java APIs" in the README): programs on the interfaces that it writes for classes of the JDK and for the classes of `tests/bind/demo/java`, with `-cp` and as a jar (their output, checked by hand, and one interface, are in `tests/bind`), with instance fields, arrays, subtypes of the interfaces it writes and a method with two results; the jar named by a `.M3EXPORTS` read with `-pkg`; classes that refer to each other, also over two runs; a supertype from an interface of the directory; `-name`, `-prefix` and nested classes; everything written for 48 classes of the JDK compiles; what it refuses. |
| `m3bundle/` | m3bundle of CM3 5.12.0 (`m3-tools/m3bundle`, with its copyright notice and manual page), which `build.sh` compiles with m3j into `m3bundle.jar`. |
| `perf.py` | Benchmarks: compiles the programs of `tests/bench` with one or more versions of m3j (`--jar KEY=JAR`, for A/B comparisons; `--cm3 DIR` for a version without its own library) and, with `--native`, with cm3 `-O`, runs the variants in turn (`--runs`, default 5) and prints the median wall time per program and variant; outputs that differ are marked. |
| `split_test.py` | Test of the splitting of large methods: generates programs whose procedures are too large for one method (over 8000 bytes, the limit of HotSpot's JIT, and over 64 KB; with large bodies of loops, `CASE`, `TRY`, `TYPECASE` and `LOCK`), compiles them with m3j, checks that every method fits and compares the output with `tests/split/*.expected` (the output of cm3). |
| `cli_test.py` | Test of the command line of the compiler (`tests/cli`): the usage message, `-run` (compiles in memory and runs the program), an option of the front end (`-NoChecks`), the exit status after an error and for an UNSAFE module, the module of an interface found in `NAMEWin32.m3` by its EXPORTS, and in the modules of a source package (`-pkg`) by their EXPORTS, without a warning for an interface of variables alone, and with the module of the name of an interface the other modules of its directory that export it too (not those of another directory), and the errors of bindings of Java classes (`tests/cli/java`); the expected results, checked by hand, are in the tool. |
| `tls_test.py` | Tests of the library tls (`tests/tls`), with keys and certificates that keytool makes for the run, without a connection to the internet: server and client in one program (data, checks of certificates, ALPN, certificates of clients, timeouts, alerts, the end of a connection; the output, checked by hand, is in `tests/tls/expected`), with the module `ssl` of Python (OpenSSL) as client and as server under TLS 1.2 and 1.3, and with a server of the JDK that starts a new handshake on the connection. `--speed` measures the rate of a transfer. |
| `http_test.py` | Tests of the library http (`tests/http`), without a connection to the internet. The escapes, dates and basic authentication against the standard library of Python, with fixed and random values; a table of requests on raw sockets with the expected status and whether the connection ends (what RFC 9110 and 9112 require of a server); framing, keep-alive, pipelining, limits, timeouts, the shutdown and failing handlers; `http.client` and `curl` as independent clients; the server over TLS 1.2 and 1.3; and the client against `http.server` of Python, and server and client in one program, over TCP and TLS (the output, checked by hand, is in `tests/http/expected`); `Content-Encoding: gzip` at both ends, with a table of `Accept-Encoding` fields, the framing, `Vary`, `ETag`, `HEAD`, flushes and failures against `zlib` of Python and `curl`, and damaged, cut off, blocked and abandoned bodies in the client. HTTP/2 needs a server that the tools do not bring and is not tested here. `--speed` measures requests per second and the rate of a transfer. |
| `xml_test.py` | Tests of the library xml (`tests/xml`), without a connection to the internet. The tokens of fixed and random documents, in several encodings and with all options for reporting, against the parser expat that comes with Python; malformed documents with the expected kind and position of the error, which expat refuses too; attacks with external entities, DTDs and entity expansion, with a local server that must see no connection; each limit just below and just above; inputs that fail, block or arrive in pieces; a generated document under a heap of 64 MB (the output of the programs, checked by hand, is in `tests/xml/expected`). For `XmlWriter` (`tests/xmlwriter`, which carries out scripts of calls): documents with their expected bytes; calls that must be refused, with a beginning of a document as the output; random documents against a model, read by expat and `XmlReader`; every character in a name, in text, in attributes and in CDATA; numbers; writers that fail or block; a generated document under a small heap, compared by hash. `--speed` measures tokens per second and the rate. |
| `zip_test.py` | Tests of the library zip (`tests/zip`), without a connection to the internet, against the modules zlib, gzip and zipfile of Python. Streams of all formats, levels and many sizes in both directions; compressed data in pieces of any size; `Wr.Flush`; all the optional parts of a gzip header; each byte of a stream changed, accepted exactly if Python accepts; each prefix; several members and what may follow them; the limit of output, also on a bomb of a gigabyte under a small heap; sources and targets that fail or block; archives with everything they may contain, archives that must be refused, and archives written for Python to read; names; many streams one after another; a stream of 2 GB under a small heap. `--speed` measures the rate. |
| `encoding_test.py` | Tests of the library encoding (`tests/encoding`), without a connection to the internet. `Hex`, `Utf8` and `Base64` over all short inputs and damaged encodings as `binascii` and the decoder of Python decide, percent escapes and queries against `urllib.parse`, references against the tables of RFC 3986 and `urllib.parse`, IP literals against `ipaddress`, times of RFC 3339 against `datetime` and tables, and what must be a checked runtime error. |
| `json_test.py` | Tests of `JsonWriter` and `JsonReader` of the library json (`tests/jsonwriter`, which carries out scripts of calls, and `tests/jsonreader`, which reads documents), without a connection to the internet. The cases `r...` are those of the reader, against the json module of Python made strict: documents with their pieces; what must be refused, with the place of the error; random documents, also damaged and in pieces of any size; every character; all short sequences of bytes; numbers to the bit; the limits; calls one by one; readers that fail or block; a generated document under a small heap. For the writer: Documents with their expected bytes; calls that must be refused, with a beginning of a document as the output; random documents whose bytes are those of `json.dumps`, and which Python and `Json` read back; every character in a value and in a key; surrogates without their partner; numbers from their bits, as texts against the grammar of RFC 8259, and the limits of `INTEGER`; the limit of nesting; keys that are there already; writers that fail or block; a generated document under a small heap, compared by hash. `--speed` measures the rate. |
| `net_test.py` | Tests of programs that talk over TCP (`tests/net/TEST`): the program runs as a server (`PROGRAM server` prints the port it accepts on) and as its client (`PROGRAM client PORT`); compiled by m3j, both must print what the server and client built by cm3 printed, recorded in `tests/net/expected/TEST` (`--record` builds the program with cm3 and records them, and the units that the build generates, such as the stubs of network objects that stubgen writes, in `tests/net/expected/TEST/gen`, which m3j compiles with the program). With `--cm3`, cm3 builds the program too, and the four pairings of servers and clients of m3j and cm3 run against the record. Tests: `echo` (TCP connections and messages), `netobj` (network objects), `gc` (the distributed collection of network objects), and the tests of cm3's netobj (`echorw`, `fd`, `longcall`, `luca`, `perf`, `pkl`, `pklWide`), whose output does not depend on times, the host or the language of the system. A server that waits for the end of its standard input ends when the client has ended. A directory `tests/net/expected/TEST/m3j-NAME` adds a run of a server and a client of m3j, whose client gets the arguments in its file `args` after the port, against outputs written by hand (`server.txt`, `client.txt`), for what the record of cm3 cannot show; `--record` leaves it alone. `gc` has one, `m3j-count`: with `count` its client also prints how many of the objects that were dropped the collectors freed, which must be all of them (the collector of cm3 frees few). |
| `diff_test.py` | Differential tests against cm3 for programs from outside m3tests (`tests/diff/*.list`: the test packages of cm3's libraries, its examples, Rosetta Code, small programs for errors found in m3j, `tests/diff/src/regress`, programs that test one area at its edges, `tests/diff/src/check` (formatting and scanning of numbers, floating-point operations, pickles, pathnames, threads under load, checked runtime errors, sets and `=` on arrays and records, the file system, TCP connections, processes and pipes, the units of the library for programs, the package sysutils, bundles and resources, weak references, the pickles of `Pickle2`, the required interfaces `FloatMode` and `Text`, the packages json and libbuf), and random programs of `expr_fuzz.py` and `prog_fuzz.py`, `tests/diff/src/fuzz`): `--record` builds each with cm3 (`cm3 -build -keep -commands`), runs it twice (a test whose runs differ is unstable) and stores the output, the units cm3 compiled, the packages it linked and the generic instances it generated in `tests/diff/expected` (a test with `result=NAME` takes the output of the record of test NAME, and one with `os=POSIX` is compiled and run by m3j for POSIX, `-Dm3j.os`; one with `expected=FILE`, for what cm3 gets wrong, is compared with FILE, its stdout checked by hand; for a program that cm3 cannot build, `check/runtime-hand`, the record is written by hand); without it, m3j compiles the same units and the run is compared (PASS, APPROX for floating-point differences within a tolerance, KNOWN for the differences listed with their reason in `tests/diff/known.txt`). |
| `coverage.py` | Coverage of m3j by the tests: runs the suites (`jvm`, `compile`, `diff`, `split`, `cli`, `m3front`, `fingerprint`, `middle`, and on request `pkg`) with the JaCoCo agent in every JVM they start (without the AOT cache, which does not work with an agent), makes a report of the classes of the build (`m3j.*` and the runtime units written in Java; HTML with the source lines marked, CSV, XML) and prints the coverage per package and the classes of the back end and the runtime with the most branches that no test executes. |
| `expr_fuzz.py` | Random expression tests of the back end: generates programs (one per seed) of checks that print random expressions over INTEGER, LONGINT, BOOLEAN, REAL and LONGREAL (arithmetic, `Word` and `Long`, conversions; operands in variables, arrays, packed records and arrays, calls and literals) and stores into packed fields and subranges, builds and runs each with cm3 and m3j and compares the outputs line by line. It computes every value itself and leaves out what is undefined in C or wrong in cm3 (listed in the tool); where cm3 and m3j differ, an integer or Boolean result tells which of them is right. Pair checks print an expression of literals as folded by the front end and as computed (`--no-cm3` compares only these). `--write DIR --list FILE` writes the programs as packages for `diff_test.py`. |
| `prog_fuzz.py` | Random program tests of the back end: generates programs (one per seed) that print a trace of what they do: control flow (`EXIT` and `RETURN` out of `TRY FINALLY`, `LOCK` and handlers, `RAISE` in handlers and `FINALLY` clauses, nested loops, `FOR` at the limits of `INTEGER` and `CHAR`, `CASE`), nested procedures that use the variables of the procedures around them, `VAR` and `READONLY` formals bound to overlapping places, copies of records and arrays, open arrays, objects (methods and the procedures that override them, calls of the overridden method, `NEW` with fields and methods, objects as formals and results) and references (`TYPECASE`, `ISTYPE`, `NARROW`, a list that is extended, shortened and walked, `REF`, `REFANY`), sets (small and large, of `CHAR`, in a packed record, an array and an object, with their operations and loops over their elements) and texts and characters (the operations of `Text`, loops over the characters of a text, `CASE` on characters, `TEXT` in `TYPECASE`), and in half of the programs several modules (procedures, procedure variables, methods, exceptions and `VAR` formals across modules, variables of interfaces, an interface that several modules export, cycles of imports, an opaque object type that one module reveals and others extend). The calls of the main body run three times, from the state the last time left, with other values. Each program is compiled by m3j twice, normally and with `-Dm3j.maxMethod=N` (a small limit, so that even small procedures are split), and both are run and compared with cm3 (PASS, FAIL, SPLIT-FAIL, VERIFY, M3J-FAILED, CM3-FAILED, BOTH-FAILED, TIMEOUT; `--no-cm3` compares only the two versions of m3j). Every program terminates and stays within what the language defines; the errors of cm3 that it avoids are listed in the tool. `--focus` weights groups of constructs (`flow`, `uplevel`, `var`, `copy`, `open`, `obj`, `set`, `text`, `mod`), `--reduce SEED` makes the program of a failed seed smaller while it keeps its status, and `--write DIR --list FILE` writes the programs as packages for `diff_test.py` (`tests/diff/prog.list`). |
| `pkg_gate.py` | Compile gate over the packages of a cm3 installation (`--cm3 DIR`, its `pkg`): compiles the modules of each package (from its `.M3EXPORTS`, with the instances of generics) with m3j `-lib`, checks that every class verifies, and counts each module as OK, UNSAFE, UNSAFE-IMPORT, ERROR, VERIFY, CRASH, BLOCKED or TIMEOUT. |
| `rosetta_prep.py` | Prepares the Modula-3 solutions of Rosetta Code (from the RosettaCodeData repository) as cm3 packages in `tests/rosetta` and writes `tests/diff/rosetta.list`: each whole, safe program is split into its units, gets a line with its origin and licence (GNU FDL 1.3) and, where the task needs it, its input. |
